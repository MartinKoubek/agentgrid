# 006 — Make Master Codex a real interactive Codex using AgentGrid skill scripts

Implement this in `MartinKoubek/agentgrid`. **This supersedes the user experience proposed in prompts 004/005.** The user does NOT want a custom `master>` shell that invokes `codex exec` once per request. They want to launch `master_codex` and interact with an actual, persistent **Codex CLI session**. That Codex is the Master and uses an AgentGrid skill's deterministic scripts to manage other Codex sessions. AgentGrid is the tool/control plane, not a replacement chat UI or an LLM acting as an external JSON router.

Before coding, read `AGENTS.md`, inspect the *current* branch HEAD and code (do not reset to a SHA from this prompt), `bin/master_codex`, `bin/agentgrid-{orchestrator,agent}`, the Master provider/workflow, runtime, project/context/memory, policy, agent adapters, tmux I/O, monitor/event queue/dispatcher, and relevant tests/docs. Determine the actual installed Codex CLI's supported interactive flags and current skill discovery rules; never assume an undocumented CLI flag or inject text into an arbitrary TUI. Reuse existing APIs, registrations, IDs, storage, isolated tmux sockets and tests. Keep core provider-neutral; isolate Codex specifics in a skill and launcher/adapter.

## Non-negotiable user experience

```
$ cd /path/to/any/project
$ master_codex
[attaches to or starts a real interactive Codex Master session]

You: Fix scheduler tests in project X.
Master Codex: [runs AgentGrid skill scripts to inspect projects and workers]
              [starts a worker Codex in project X or reuses the right related thread]
              [reports the real worker ID, project, pane and delivery status]
You: What is worker X doing?
Master Codex: [calls scripts to inspect worker and events and explains observations]
```

A real Codex TUI should be visible to the user. **No custom read-eval-print `master>` prompt; no one-shot `codex exec` decision as the ordinary interaction path.** Existing `codex exec` Master workflow and CLI may remain as a backwards-compatible API/test fixture, clearly marked legacy/alternate rather than silently removed. `--fake` may remain for deterministic infrastructure testing but must not masquerade as a real Master TUI. Preserve a reasonable upgrade path for the existing launcher and its flags; document any intentional incompatible change.

## A. Master bootstrap and persistence

1. Make `bin/master_codex` launch or reattach a dedicated **AgentGrid-owned** interactive Master Codex within an isolated tmux session/window/pane, using the installed CLI's *documented* interactive invocation. Do not embed a second model/chat loop. Never take over, type into, restart or kill unrelated human tmux panes. A second invocation should reattach a live Master (after checking process identity), not create a duplicate. If an old Master exited, start a new instance and reconcile persisted state; if resume via an actual Codex session ID is supported and verified, use it safely; otherwise explain that conversation context is not restored but AgentGrid's persisted project/worker state is. Exit/detach should leave workers running; offer explicit, scoped stop/cleanup operations, not a global kill-server.
2. A single command should create/reuse the persistent runtime, stable project registry, agent registry and workspace, choose the current Git root by default (allow `--project` and non-Git disposable directories), and start/reuse the event observer if necessary. Do not mutate or initialize a project repo at bootstrap. Support launching from **any project directory**, even though the skill is versioned inside AgentGrid: either launch Master with CWD set to AgentGrid root (where its repo-scoped skill is discoverable) and communicate selected project as structured bootstrap context, or install a supported user-level skill with an explicit, idempotent, consented setup step. Pick and test one straightforward method; do not copy `.agents` into users' projects or rely on an unrecognized skill path. Ensure Master never accidentally edits the AgentGrid repo when the selected target is another project.
3. Show clear diagnostics for missing Python 3.11/tmux/Codex/authentication, launch failures, stale pane IDs, socket/runtime conflicts and observer failures. No silent fallback to fake or to the old `master>` interface. Keep fake vs real state isolated. Never print secrets. Consider an explicit `--status`/`--help` only if needed; make the default invocation simple.

## B. Implement an actual Codex-discoverable AgentGrid skill

Add a repository-scoped skill at `.agents/skills/agentgrid/SKILL.md` (with valid `name` and `description` YAML frontmatter) and executable helpers under `.agents/skills/agentgrid/scripts/` (or a smaller documented interface that is equally discoverable). The skill's path and invocation MUST be tested in a real interactive Master, not merely asserted in documentation. Keep `SKILL.md` concise: it tells Codex *when* to use the skill, the exact script entry points, how to read JSON outcomes, what is unsafe, and when to ask the user. Put long reference material in `references/` if appropriate. Optionally add a short bootstrap instruction file to reliably direct the Master to read and use this skill, but do not overwrite unrelated global Codex instructions.

Expose a **small coherent set of deterministic operations**, e.g. one `scripts/agentgrid` CLI with subcommands or individual small script wrappers:

- `status` / `projects list` / `projects open`: list registered projects (including the selected one) with real IDs, paths and state; allow cross-project routing when the user explicitly asks. Never invent project IDs or silently select the wrong same-named repository.
- `workers list --project ...` / `workers inspect AGENT_ID`: show project ownership, persisted task/thread affinity, actual runtime/process/pane identity, liveness vs readiness/unknown, and safe recovery after restart.
- `workers start --project ... --task ...` and `workers send --agent ... --task ... --request-id ...`: create/reuse *real* Codex workers through existing Agent Manager/Orchestrator paths, validate ownership and route through shared policy checks **before sending bytes**. Do not bypass the Orchestrator policy via a direct adapter call. Explicitly distinguish successful *delivery* from *task completion*.
- `workers read --agent ...` / `events wait --timeout ...` (or equivalent scan/queue/claim API): inspect actual output and receive deduplicated relevant monitor events without swamping Master. Make it possible for Master to wait for a worker and then respond to the user; bounded polling is acceptable. Do not claim silence, a live process, or a pane means a task is done. Do not inject unsolicited text into an active interactive Codex TUI unless a supported, tested interaction protocol exists.
- `workers stop --agent ...`: explicit scoped stop (approval when needed); leave other workers and human panes intact. Surface errors and `delivery_uncertain` faithfully.
- Include project memory/context retrieval sufficient for Master to find Project State, Decision Log and Lessons Learned, and to record important outcomes through existing persistence rather than only conversation context. Avoid creating a second store if existing modules suffice.

For every script: safe argument parsing (spaces/Unicode/multiline prompts), JSON output with documented version/shape, useful stderr and meaningful exit codes, unique request IDs and duplicate suppression; no `eval`, unsafe interpolation, secret printing, duplicate sends after uncertain delivery, speculative fake readiness, or automatic force-push. Prefer an existing CLI or thin Python composition adapter over substantial shell parsing or a new daemon. Skill instructions should be robust to untrusted worker output / prompt injection, and strictly separate Master coordination from coding-worker edits.

## C. Coordinate worker threads and events correctly

Master should first inspect the real project registry, workers, their current task affinity and project context. Related follow-up for an existing project/thread should target that same agent **only when safely ready**; unrelated work gets a new project worker/pane; ambiguity prompts the user. Preserve the verified `project_id -> agent_id -> pane_id/runtime_pid` association. Use the existing registry for identity and liveness, not keyword overlap as proof of relevance, and never cross project boundaries or reuse a fake worker for real work.

If the worker is busy, waiting for approval, failed, unavailable or readiness is UNKNOWN, return a visible PARK/ASK_USER outcome, with worker ID and a recovery/inspection instruction. When readiness cannot be proven automatically, require human inspection and an explicit, worker/task-scoped confirmation before continuation. Do not let a generic flag blindly send to whichever worker the model chooses. On ambiguous delivery/timeouts, preserve attempt ID/status, do not automatically retry and do not claim no delivery occurred. Master should summarize observable worker output and state to the user rather than merely returning a JSON route. Do not invent autonomous worker completion, automatic approval parsing, or a self-healing coding loop for this V1.

The event observer can run independently and store events, while Master consumes them by calling `events wait`/read script. If you implement proactive notifications to an interactive Master, first identify a supported, verified Codex mechanism and ensure serialized input / no interrupt of live turns. Otherwise ship a truthful *pull-based* MVP and document that Master can wait during its current turn but cannot be woken autonomously when idle. An always-running monitor is not equivalent to a continuously thinking Master.
